## 2026-11-21 发布门禁拆分

`release.yml` 里"推 tag 即公开"只靠 `if: github.event_name == 'push'` 一道判断：没有批准记录、没有制品摘要比对，同名 Release 还走 `--clobber` 覆盖。`verify_release_apk.py` 的递增门把 `PUBLISHED_VERSION_CODE = 100` 写死，而 101/102 早已发布——这道门是空的。

拆成两个工作流：`Release Candidate` 只构建校验、上传 artifact，summary 打印 tag / run_id / SHA-256；`Publish` 需 `release` environment 批准，下载指定 run 的 artifact，先比摘要再比 tag 指向的提交与 run 的 headSha，最后才创建 Release。已存在同名 Release 时改为"摘要相同幂等、不同则失败并保留原附件"。

递增门改成参数：`version_code(tag, published)` + `max_version_code(tags)`，workflow 从 `gh release list` 求最大值传入。

顺带把 actionlint 装到本机跑了一遍，正好命中 `SC2129`（`echo ... >> "$GITHUB_OUTPUT"` 三连），改成块重定向后清零；CI 增加 actionlint 步骤防回归。

教训：`--clobber` 这种"方便重跑"的写法，本质是把"这次发的是什么"这件事抹掉了。

## 2026-11-21 结果交付与轻提示分离

转写结果和"已插入""太短了"这类轻提示挤在同一个 `MutableSharedFlow(extraBufferCapacity = 16)` 里，用 `tryEmit` 发射。只要 UI 侧的提示通道（`toasts.send`）挂起一次，缓冲区满，后面的 `tryEmit` 直接返回 false——用户的听写文本就这样静默消失了。丢的恰恰是唯一有产出的东西，而提示丢了无所谓。

拆成两条通道：结果走独立无界 `Channel` + `send`，慢消费者只会让发送方挂起；轻提示保持 `tryEmit`，允许丢。

交付语义也分开：`markDelivered` 负责发射去重（同一 resultId 只发一次），新增 `confirmDelivered` 记录"UI 真的插进去了"，供诊断与测试断言。

验证：新增 `ResultDeliveryTest`，用闸门卡住消费者前 20 条，让 100 次转写压进去——把实现临时退回 `Channel(16)` + `trySend` 时用例失败（只收到 20 条），恢复无界 `send` 后 100 条各一次通过。全量 100 例单测通过。

顺带确认 `Release Candidate` 端到端可用：`-f tag=v0.1.3` 的 run 44854295396 成功，summary 给出 versionCode 103、SHA-256 `3af63385…`、run_id，artifact 已上传（Publish 需 `release` environment，尚未创建）。

## 2026-11-21 录音截止与转写中的路由变化

两个问题都出在"时间"和"阶段"的判断上。

**截止按样本量算**：`PcmAudioRecorder` 用 `sampleCount >= capacity` 判断到顶，`DictationController` 的 ticker 也只看 `capture.currentDurationMs`。设备一旦长时间零读（不返帧），样本量不增长、时长永远停在 0，录制就永远不会自动结束——用户卡在 RECORDING，AudioRecord 也不释放。

改成墙钟：controller 注入 `nowMs`（默认 `System.nanoTime()/1_000_000`，保持 core 的 android-free，测试里传 `testScheduler.currentTime`），ticker 用 `nowMs() - recordingStartedAtMs` 判截止；recorder 的读循环再用 `SystemClock.elapsedRealtime()` 兜一层，保证 controller 不在时也能释放设备。零帧的兜底截止不算"录到上限"（`durationCapped = sampleCount > 0`），否则会把空音频送进识别，这里按误触走 `TooShort`。

**转写中拔耳机丢结果**：`AudioRouteInterrupted` 之前对 `CANCELLABLE_PHASES`（含 TRANSCRIBING）一律 `cancelActive()`。音频都已经采完在识别了，此时路由变化把会话取消，等于凭白吞掉用户刚说的话。改成只在 STARTING/RECORDING 取消并提示，TRANSCRIBING 继续。

验证：新增两个 JVM 用例——零读时 31s 虚拟时间后仍能收敛到 READY 且只提示 TooShort；转写中派发路由中断后 5s 延迟的识别仍交付。把截止判断改回样本量时第一个用例失败，恢复后 102 例全绿。

## 2026-11-21 草稿不进 saved state，以及墙钟截止的修正

**草稿留在进程内**：`rememberSaveable(TextFieldValue.Saver)` 会把用户正文写进 saved state，转屏能活，但也会跟着系统快照/备份落到别处——与"不上传、不留存"的隐私基线相冲突。改成 `remember(viewModel)` 从 VM 播种：转屏仍保留（VM 跨配置变化存活），进程被回收则丢弃。收益是正文彻底不进 Bundle，代价是后台被杀后草稿丢失，与 PRD 现状一致。

**墙钟截止修正**：昨天那条"改成墙钟"在真机上翻车——`AudioRecordLifecycleTest.durationCapAutoStopsRecording` 只采到 22400 个样本（预期 24000）。原因是读循环首帧到来比 `elapsedRealtime()` 起点晚，30s 墙钟到点采还没攒满。判断改成"连续 30s 没有新样本才退出"：正常采集每帧都会刷新进展时间，永远不会触发；设备零读时才兜底释放。测试恢复精确的 24000 样本。

顺带修了压力测试：`LongRunDictationStressTest` 还在收 `controller.events` 等 `TranscriptReady`，结果通道拆分后自然一条也收不到，改为收 `controller.results`。

验证：真机全量 36 个仪器用例通过（含转屏 3 例、压力 1 例、AudioRecord 7 例）。

## 2026-11-21 英文句界、无障碍与键盘

**句界**：`joinTranscripts` 只看相邻两字符，`Hello.` + `World` 落到"标点不加空格"分支，拼出 `Hello.World`。加一条句界规则：英文句末标点 `. ! ?` 后接文字字符补空格，中文句末标点 `。！？` 只在后接拉丁时补；小数与版本号（`.` 前是数字且后文以数字开头）例外，`3.` + `5` 仍是 `3.5`。插入路径与拼接路径共用同一判定，避免两处行为漂移。

**无障碍**：分段控件选中态原来只有填充色，色觉障碍下与未选中难以区分，选中项加勾选图标作为非颜色标记。按住按钮对 TalkBack/外接键盘不可用（无法"按住"），补一个自定义无障碍动作：READY 时"开始语音输入"，其余可交互态"结束并转写"，一次点击完成等效操作。

**Snackbar**：宿主原来只做 `align(BottomCenter)`，键盘弹起或导航栏存在时会压在下面，补 `navigationBarsPadding()` + `imePadding()`。

验证：单测 106 例、真机仪器测试 37 例（新增 1 例断言自定义动作存在且能触发开始）；浅色/深色截图确认勾选标记可见，短录音提示条位于手势条上方。

## 2026-11-21 草稿改为跨进程保留

上一轮把草稿从 saved state 里摘掉后，进程被回收就丢了。现在改成写应用私有 SharedPreferences：`DraftStore` 抽象存储、`DraftKeeper` 管防抖、`SharedPreferencesDraftStore` 用 `commit()` 同步落盘（草稿只有一条文本，同步写完才敢让进程在下一帧被杀）。

防抖 320ms：按键停下才写一次；转写结果插入这类不能丢的节点走 `immediate`；`onCleared` 再补一次 `flush`，避免最后一次输入落在防抖窗口里丢掉。

可测性上把调度从 ViewModel 抽出来：`DraftKeeper` 只依赖 `DraftStore` + `CoroutineScope`，JVM 用 `TestScope` 断言"319ms 不写、321ms 写一次、中途再输入会重置窗口"；真实存储用仪器测试验证往返与 ViewModel 恢复。全量单测 116 例、仪器测试 41 例。

## 2026-11-22 评测语料：用合成语音先立一条线

第 4 节的语料一直是空模板，评测用例 `assumeTrue` 直接跳过。真人语料没法凭空造，所以先用 TTS 合成 90 条（zh / en / mixed 各 30，16kHz 单声道，平均 2.52 秒），生成脚本 `scripts/gen_corpus_tts.py` 一起进库，保证可复现。

首位基线：zh CER 1.66%、en WER 2.08%、mixed CER 2.74%，RTF p95 在 0.08–0.10 之间，引擎单条 130–260ms。

这套数字的意义要说清：**它只能证明链路没坏，不能证明真人好用**。合成语音没有口音、语速突变、口吃重复、背景噪声和远场混响，而这些正是端侧听写最容易翻车的地方。所以我在 `AsrAccuracyEvalTest` 里加了 10% / 10% / 12% 的回归门槛——约为实测值 3–5 倍，超限直接失败并打印该语言最差 5 条，避免"跑完没人看日志"。

真人的事还得真人来，语料目录留好了位置，后续按句追加即可。

## 2026-11-23 机型矩阵：先把"测了什么"说清

手头只有一台 Redmi（Android 14 / arm64），所谓"矩阵"其实只能覆盖一个点。所以这轮没去凑设备，而是把三件事做实：`docs/device_matrix.md` 列清维度与逐项证据，`scripts/run_device_matrix.sh` 让"接上新设备跑一遍"变成一条命令，以及把今晚发现的两个真问题写进去。

第一个问题：跑全量 42 项时设备重启了（`uptime` 归零、`INSTRUMENTATION_ABORTED: System has crashed`），而单独跑评测、音频生命周期、分段器、模型冒烟都正常。没定位之前不把长稳用例塞进默认全量流程。

## 2026-11-23 矩阵收口：两个待查项各有结论

长稳用例单独跑是好的（`OK (1 test)`），评测单独跑也是好的。问题只出现在同一进程里"先评测 90 条、再开 100 次会话"，所以文档里把条件收紧成这一条，不再说"长稳跑不动"。

转屏第三例挂住是我自己写测试的疏漏，两处：真实 ViewModel 的 PREPARING 动画让 `waitForIdle` 永不返回；用例之间共享真实 SharedPreferences，前一个用例打的字被后一个用例的 VM 恢复出来。修法是关掉自动推进、手动推帧，再给每个用例注入内存版 DraftStore。修完 `OK (3 tests)`。

脚本也补了一条：MIUI 拦后台启动时 instrument 一声不响挂着，光靠墙钟超时要等半小时，改成"用例标记 150 秒不增长就判定停滞"，脚本自己能说清是"被系统拦了"而不是"跑得慢"。

## 2026-11-24 矩阵第一次真正跑绿

`--in-place` 一轮：主批 `OK (41 tests)`、长稳 `OK (1 test)`，合计 42 项 0 失败，462 秒。这是这套仪器测试第一次在真机上完整通过。

过程中被自己的脚本坑了两次，都记在这里：

1. **停滞判定会误杀长用例**。长稳整场只报一次 test 标记，按"标记 150 秒不增长"判定，跑到 150 秒就被判 stalled 杀掉。改成单类派发时关掉停滞判定（`STALL_IDLE=0`），只留墙钟上限。
2. **全绿时没有 `Tests run:` 行**。JUnit 只在失败时打印 `Tests run: N, Failures: M`，全绿只打 `OK (N tests)`，于是汇总把 42 读成 0、判成 fail。改为先解析 `OK (N tests)` 再叠加。

这两条都是"判据写得太想当然"——用"有没有新用例开始"判断"是不是还活着"，在单例长跑上不成立；用"有没有 Tests run 行"判断"跑了多少"，在成功路径上不成立。

## 2026-11-24 第二台设备：Android 17 的真实差异

拿到 OnePlus PJZ110（Android 17 / API 37）后，第一次跑测试全线失败，三条互不相干的原因：

其一，Espresso 3.6.1 在 API 37 上调用已被移除的 `InputManager.getInstance()`，所有 Compose 用例在 `waitForIdle` 里崩。升到 3.7.0 后恢复。

其二，Android 17 起 shell 不再持有 `GRANT_RUNTIME_PERMISSIONS`，`pm grant` 和 `GrantPermissionRule` 都直接抛异常。改成"尽力授予、失败记账"的规则，把权限前置条件交还给人工，而不是让规则层统一报错把原因藏起来。

其三，跑重负载用例时进程被杀，`am instrument` 只说 `Process crashed`。翻 `logcat` 才看到是 ColorOS 的 `OsenseKillAction` 在按内存回收，`oom:FGS` 也没护住——不是我们的 bug，是 OEM 策略。

轻量用例最终 36 个全过，模型推理本身在 API 37 也正常。剩下的两个重负载用例需要先加白名单，这条写进矩阵文档，没有假装跑通。

## 2026-11-24 找到了 ColorOS 杀进程的真正条件

上一轮把重负载用例被杀归因于"内存占用 400MB"，试过 Doze 白名单、活跃桶、亮屏、周期性触摸，全都没用。真正的原因是**没有窗口**：`AsrAccuracyEvalTest` 和长稳只做推理、不启动 Activity，ColorOS 的 `OsenseKillAction` 把无窗口进程判为可回收，`oom:FGS` 也不护。

改法很小：用例在推理前 `ActivityScenario.launch(MainActivity::class.java)`，跑完关闭。两个用例各自 `OK (1 test)`，全量套件 `OK (42 tests)`。

教训：OEM 的"省电/清理"策略未必按内存阈值判断，先看它到底依据什么信号——这次是窗口可见性，不是 RSS。

## 2026-11-25 权重许可不是 MIT

清单里把 SenseVoice 权重记成「MIT（经 FunASR 仓库 LICENSE）」，这是 PRD §6.4 明令禁止的做法——拿代码仓库的许可去代表模型权重。查 ModelScope 模型页 `iic/SenseVoiceSmall` 的 `License` 字段：**Apache License 2.0**。

两者都是宽松许可，但义务不同：Apache-2.0 需要随产物附带 NOTICE，MIT 不需要。所以这不是文字游戏，是分发时要多做的一件事。

顺带核清另外两条：HF 镜像没有 model card 许可声明（不能当依据）；sherpa-onnx 内置的 ORT 是多 EP 构建，但 APK 没打包 `libQnn*.so`、运行期固定 `provider = cpu`，分发物里不含 QNN/NNAPI 专有二进制。
